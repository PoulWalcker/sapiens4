# Development packaging and release runbook

These commands prepare the `PoulWalcker/sapiens4` development fork/channel and
`com.poulwalcker.sapiens4.development` identity. They do not enable production
update discovery. The active wave permits local builds and commits. Pushes,
workflow dispatch, release creation/publication, live accounts and real user data
require separate authorization; none are executed by this runbook itself.

## Assemble and verify locally

1. Use the assigned worktree explicitly. Record its source commit, dirty status,
   exact libs4/Blindly pins and toolchain versions. Build GHC 9.14.1/Cabal 3.18.2,
   Rust 1.99.0 and the UI from pinned inputs. `--skip-build`/`-SkipBuild` cannot
   certify that existing binaries came from those recorded inputs.
2. Acquire the complete verified provider using D3's `acquire-provider.py` after
   main integrates it. Preserve its upstream layout, helpers, resources and
   notices. Pass the entire directory to the platform build script. Missing or
   modified inventory entries, symlinks and extra files fail staging.
3. Use a new output directory. macOS defaults to deployment target/minimum 13.0
   and fails if required/unknown Mach-O code requires a higher OS. The exact locked
   Codex 0.167.0 voice subtree has one audited optional exception, bound to the full
   upstream provider inventory. Source and released-CLI sentinel evidence shows
   selected login/status/exec paths do not enter it. Every non-system load-command
   dependency stays inside its required or optional boundary; optional voice's
   declared maximum 14.0 is recorded separately. All payload remains inventoried
   and signed. This does not certify execution on macOS 13. An explicit
   `--experimental-minimum-os` is still a local experiment rejected by the
   draft-release validator.
4. Platform assembly relocates dependencies and signs nested code first. The
   original provider inventory is preserved as `sapiens-provider-upstream.json`.
   `sapiens-provider.json` then describes final packaged bytes, including the
   preserved original inventory. `package-inventory.json` covers all runtime
   files except itself, including the final package manifest. Verify with:

   ```sh
   python3 build/package/package.py verify --runtime /absolute/path/to/runtime
   ```

5. On Mac, final app signing seals the inventories. Notarization/stapling, when
   configured, follows composition. ZIP creation is last; the adjacent
   `.release.json` binds the final asset name, byte size, SHA256 and package
   manifest hash. `buildId` identifies recorded source/dependency/provider/build
   inputs before signing; it does not promise reproducible signed bytes. Never
   embed an artifact's own digest inside that artifact.
6. Run one RSpec installed-runtime scenario with `SAPIENS_TEST_PACKAGE_RUNTIME`
   pointing at the output runtime. It checks final inventories/provider version,
   real backend HTTP/assets on two launches, unchanged synthetic identity and
   graceful exit. `smoke.py` is only its command probe; RSpec owns assertions.

Source exports need `build/source-provenance.json`, generated by
`python3 build/package/package.py provenance --output build/source-provenance.json`
in the exporting checkout. Packaging Python is a builder dependency, never an
end-user dependency. Source distribution and existing platform tests remain.

## Signing setup and exact artifacts

Set up publisher identities in a dedicated protected signing context after account
authorization. Keep PR build jobs credential-free. Do not print/import/export
secrets in ordinary build logs.

For a configured Mac Developer ID identity and an already configured notary
keychain profile, the concrete assembly command is:

```sh
./environments/macos/build.sh --version 0.1.0-dev \
  --provider /absolute/verified/codex --output-directory /absolute/new-output \
  --sign-identity 'Developer ID Application: ORGANIZATION (TEAMID)' \
  --notary-profile sapiens4-development
```

The script uses hardened runtime/timestamp signing, strict deep verification,
notarytool submission, stapling/validation and Gatekeeper assessment. Ad-hoc
signing is the local default and supplies no publisher/notary trust evidence.
Do not strip the provider's optional helpers or rewrite binary OS load commands
to bypass a compatibility failure.

For an already configured Windows certificate in the appropriate certificate
store and a Windows SDK SignTool on PATH:

```powershell
.\environments\windows\build.ps1 -Runtime win-x64 -Version 0.1.0-dev `
  -ProviderDirectory C:\verified\codex -OutputDirectory C:\new-output\Sapiens4 `
  -CertificateThumbprint CERTIFICATE_THUMBPRINT
```

Each EXE/DLL is SHA256 signed, timestamped and verified before final inventory
refresh and compression. Installer/helper signing must be added when installer
integration lands. An unsigned ZIP or publisher signature alone is not proof of
successful installation or absence of SmartScreen prompts.

After genuine signing, separately verify the exact downloaded/quarantined Mac
artifact on the target OS, and the Windows downloaded/installed artifact on native
Windows. Check shell/host/Blindly, permissions, WebView2 preflight, shutdown and
D3 onboarding with authorized synthetic/designated-account contexts. macOS 13,
Windows x64 and Windows 11 ARM emulation acceptance remain explicit gates.

## CI and separately gated draft release

`native-build.yml` initializes fixed dependency commits using explicit upstream
URLs (including Blindly's relative-URL override), pins toolchains, acquires D3's
provider, builds macOS arm64 and Windows x64, then runs the RSpec package scenario.
It uploads build artifacts only. The acquisition script and unpublished libs4
registration must be integrated by main before a remote run can work.

Default macOS assembly accepts only the pinned audited optional voice exception.
A new provider pin/subtree or a required dependency reaching it requires another
audit; it cannot inherit an exemption by directory name. Do not add an experimental
floor override to CI to turn a compatibility failure green. Native runner architecture is
asserted. Runner images may change despite fixed OS labels; record tool versions
and input pins rather than claiming byte-for-byte reproducibility.

Only after separately authorized push/dispatch and review of a successful trusted
build, invoke `release-development.yml` on the fork's main branch with the explicit
run ID, matching `dev-vSemVer` and `authorize_draft=true`. Configure the protected
`development-release` environment before use. Its validator requires exactly two
complete target receipts, common version/source, clean source state and exact
artifact hashes. Experimental support-floor artifacts are rejected. It creates
only a draft prerelease; publishing/promoting it is another authorized action.
The script does not overwrite an existing release or enable installed update
checks. Actual CI execution, account setup, per-user Windows installer and
production signing/publication are outstanding delivery work.
