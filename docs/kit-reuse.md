# Personal Kit reuse

Preparation can automatically select a checked Python script from this Sapi's personal
Kit catalog instead of generating its source again. The catalog shows immutable artifact
identity, original goal/criteria summary, provenance, required language/runtime,
dependencies/capabilities and personal scope. Original consumer inputs, observations and
result/effect receipts are not supplied as catalog context. Catalog summaries are bounded;
omissions are reported. Cross-owner, Group and standalone task reuse are not included.

A compatible script keeps its exact bytes. The host does not translate it into Haskell or
install dependencies. Structural applicability checks owner/scope, execution interface,
input/content family, pinned runtime/version and capabilities. Actual environment
availability is verified during preparation; the catalog alone is not an execution grant.
Missing, changed, unavailable or known faulty artifacts give an explicit refusal. Known
faulty bytes cannot become eligible again merely through a different checked wrapper.

The second Routine receives its own immutable candidate reference, accepted contract,
current input binding, independent fixtures and review. It still requires its own
independently authorized occurrence and activation audit. It never inherits the first
Routine's acceptance, activation, business result, delivery or external-effect authority.
There is no new three-exploration-run prerequisite. Normal preparation remains available
when no compatible artifact fits.

For a hybrid, only calculation bytes and structural content family are reused. Its new
explanation instruction, accepted contract/criteria, rubric, model/template pins and actual
explanation checks belong to the target consumer. Source instructions/narratives and
source endpoints/cursors/profile identities are not copied as authority.

Artifact identity and the new consumer candidate digest are distinct. Complete immutable
script/runtime metadata is stored in the target's own preparation; origin references then
serve as provenance. Changing or deleting the first Routine does not alter the target's
binding or require its mutable history at execution. Existing stored preparations remain
the artifact storage owner; this adds no marketplace, registry table or automatic upgrade.

Selection revalidates current source bytes/scope/fault status and publishes the target
wrapper under one guarded transaction. Isolated checks and business execution resolve the
target's own canonical bytes and Kit descriptor again. Missing/tampered local content is
refused before execution. Existing consumers are not silently updated or reassigned when
another source changes or becomes suspect.

When a calculation fault identifies shared bytes, other consumers retain their exact pin
and history while using ordinary LLM execution until a local inspection resolves their
applicability. Explanation-only faults do not mark calculation bytes suspect. Inspection
is automatic, response-only and deduplicated for the same issue, consumer binding and
contract. Its persisted 90-second deadline is a sublimit of the existing repair-case
allowance; retries, refreshes and restart do not grant fresh inspection time. Existing
unrelated repair activity is preserved. An unknown inspection remains visibly held rather
than repeating indefinitely. Existing uncertain-effect guards still apply to ordinary
execution and inspection admission.

An unaffected verdict authorizes only that consumer's exact current binding and contract;
it does not clear the shared suspect fact. An affected verdict enters that consumer's own
bounded repair using the same case ledger. A repaired version accepted by another
consumer is a proposal, not an upgrade authorization. Preparation, independent checks,
an authorized occurrence and its activation audit still belong to the receiving consumer.
The final activation compares its expected prior binding and current contract; Stop,
deletion or superseding changes prevent a late inspection or upgrade from taking effect.

The existing Routine UI shows shared suspect status, local inspection evidence, checked
consumers, proposed versions and the expected prior pin for its own upgrade. Case Stop
cancels future inspection/repair admission without changing the retained active pin.
