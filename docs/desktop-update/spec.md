# D2. Обновление установленного приложения

Проект спецификации для `feat/update` от `release/nov-16` (`666a028`). Первая поставка охватывает macOS arm64 и Windows x64, у версий A и B совпадают все поддерживаемые форматы состояния. Data Root, каталог конфигурации и профиль окна сохраняются. Версия схемы SQLite 8 служит одной из контрольных точек испытания. Преобразования данных, резервные копии для миграций и откат бинарников находятся за границей этой поставки.

### Пользовательский сценарий

1. При старте и периодически во время работы shell проверяет метаданные стабильного канала. Базовый интервал, предложенный для первой поставки, — сутки. Подходящая более новая версия появляется в локальном интерфейсе как **Update & Restart** с номером B. Обычные запуск, Quit и повторное открытие дают ноль запросов за пакетом.
2. Один клик разрешает попытку установки конкретной B для этой установки и платформы. При изменении предложения показываем новую версию и ждём нового клика. Повторное нажатие не создаёт второй загрузки. Выбор удалённой Corpora меняет рабочий контекст, обновление всегда адресовано локально установленному приложению.
3. При работающей задаче, принятой очереди или активации локальной дочерней Corpora A сообщает «Завершите текущую работу и повторите». Работа продолжается, запросов за пакетом нет. Будущее расписание и ожидание решения пользователя сами по себе обновлению не мешают.
4. Когда backend свободен, он закрывает приём работы и штатно завершается. Shell проверяет выход и потомков. После получения исключительного владения установкой начинается загрузка. Пока рабочий backend остановлен, shell показывает версию, этап и при наличии данных прогресс. При обычной работе разные Data Root могут быть открыты одновременно. Другая живая сессия этой установки блокирует замену.
5. После начала загрузки потеря shell не снимает защиту. Повторный запуск A, в том числе с другой конфигурацией и пустым вторым Data Root, показывает статус обновления до открытия хранилища. Код 75 был наблюдаемым признаком отказа тестовой сборки. Для пользователя критерием служат понятный статус, отсутствие второго backend и пустой каталог.
6. После проверки пакета и успешной замены запускается одна B из прежнего места установки с исходным Data Root и конфигурацией. В рабочем окне видны созданная ранее запись и та же Corpora. При несовместимом контракте форматов пакет исключается из этого канала совместимости уже на этапе предложения.

### Ошибки и восстановление

| Наблюдение | Что видит пользователь и что делает приложение |
|---|---|
| Нет сети при проверке метаданных | A продолжает работу. Следующую проверку можно повторить. |
| Пропало подтверждение остановки, потребовалось принудительное завершение или остался живой потомок | Shell сообщает об ошибке остановки. Запросов за пакетом и запусков установщика — ноль. Перед повторной попыткой shell устанавливает фактическое состояние backend. |
| После остановки A оборвалась загрузка либо отклонена подпись, замена заведомо не началась | Владелец попытки удаляет её временные файлы, снимает запрет запуска и позволяет снова открыть A на первом корне. Следующая загрузка требует нового клика. |
| Установщик мог начать замену, результат неизвестен | При повторном открытии показываем восстановление установки. До подтверждения целостности и завершения установщика рабочий backend закрыт. Ремонт использует проверенный пакет для этой установки. |
| Windows сообщил о необходимости перезагрузки | Показываем требование перезагрузки. После перезагрузки проверяем установленную версию и результат замены перед открытием workspace. Автоматической перезагрузки нет. |

### Что уже доказано

В `ba3342d` тест нажимал видимую кнопку установленной A через accessibility, удерживал архив после 256 КиБ, проверял выход backend, завершал shell и запускал тот же исполняемый файл на втором корне. macOS прошла дважды. На Windows после исправления длины тестового AppId Inno завершился с кодом 0. На обеих платформах повторный A вернул 75, второй каталог остался пустым, B открыла первый workspace с прежними идентификаторами. Это автоматические прогоны. Новые ручные приёмки перечислены в плане.

В испытании работали внешние тестовые помощники. На Mac использовались локальная подпись и одноразовый ключ EdDSA. На Windows использовались ожидаемый SHA-256 тестового пакета и сеанс Administrator в режиме установки для текущего пользователя. Для выпуска отдельно проверяем подпись издателя, автономность поставки, доступ обычного пользователя и восстановление после ошибки замены.
